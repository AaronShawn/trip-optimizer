# 算法细节与调参指南

## 问题形式化

这是 **多日带时间窗的路径规划问题**（Multi-Day VRPTW 变体）：

- **节点**：候选 POI，每个有服务时长 `visit_min`、时间窗 `[open_time, close_time]`、收益 `rating`
- **车辆**：天数。每辆车有工作时段 `[day_start, day_end]` 和容量 `max_pois`
- **弧**：真实路网耗时 `T[i][j]`（分钟），非对称（单行道、立交桥导致 A→B ≠ B→A）
- **约束**：
  - 硬约束：时间窗、闭馆日、每日时段上限、用餐窗口
  - 软约束：必去点覆盖、每日负载均衡、避免长距离跳跃

NP-hard。精确解在 POI > 15 时不可行，所以用启发式。

## 为什么不用 OR-Tools

`ortools` 的 `RoutingModel` 能解这个，但：
1. 时间窗惩罚需要在模型里显式建模，权重难调
2. 我们要的"可解释性"（每段为什么这样排）它给不了
3. 安装了 ortools 反而让 skill 有依赖，跨机器不可靠

自研的三段式启发式在 15–30 个点上，解的质量与 OR-Tools 通常差 3–8%，但快、可解释、零依赖。点数再多可以考虑切回 ortools（`trip_opt.py` 已保留 `HAS_ORTOOLS` 探测）。

## 三段式求解

### 阶段 1：全局贪心插入

按 `(priority, -rating, -visit_min)` 排序，逐个把点插入到"边际代价最低 + 负载最轻"的那一天。

边际代价：
```
Δ = [cost(插入后当天) - cost(插入前当天)]     # 目标函数增量
  + balance × max(0, 当天当前收工时刻 - 其他天平均收工时刻) / 60
后乘以优先级系数：{1: 0.2, 2: 0.6, 3: 1.0, 4: 1.5}
```

**为什么用"收工时刻"做均衡而不是点数**：6 个 30 分钟的快餐点和 2 个 3 小时的博物馆，点数差 3 倍但时间可能一样。真正让人难受的是「某天下午三点就没事干」。早期版本用点数均衡，实测出现了 Day1 只排 2 个点、Day3 排 6 个点的情况。

闭馆日在候选天里**预先排除**，不进入目标函数——这是硬约束，用惩罚处理会漏。

### 阶段 2：跨日局部搜索

三种邻域动作，直到总代价（含均衡项）无法下降：

| 动作 | 说明 | 触发场景 |
|---|---|---|
| 补插 | 前面因代价被拒的点，重新尝试插入任意一天 | 某个点的 priority 后来被提高 |
| 移动 | 从某天摘一个点，插到另一天的最优位置 | 某天过载 |
| 交换 | 两天各出一个点互换 | 减少总交通，同时不改变负载 |

关键实现细节：**判断是否接受必须用全局总代价**（`total_cost(cand_routes) < total_cost(routes)`），不能用局部两天代价。用局部代价时，均衡项不参与，永远不会为了均衡而移动——这是早期版本 Day1 只排 2 个点的直接原因。

### 阶段 3：单日路线排序

1. **2-opt**：反转区间 `route[i+1..j]`，接受则继续
2. **or-opt**：单点移位到任意位置
3. **LNS 破坏重建**：随机摘 1–2 个点，随机插回，再跑一次短 2-opt；接受更优解。这是跳出 2-opt 局部最优的关键，200 次迭代。
4. 再跑一遍 2-opt 收尾

## 目标函数

```python
cost = w_travel  × 总交通分钟
     + w_penalty × 时间窗违规
     + w_value   × Σ(6 - rating) × (5 - priority)
     + w_ticket  × 门票总额
     + Σ stretch(超长路段)
```

时间窗违规分三档，权重差异很大：

| 情形 | 系数 | 理由 |
|---|---|---|
| 早到等待 | × 0.8 | 等开门是正常的，轻微扣分 |
| 迟到（挤占游览时间） | × 8 | 强罚，实际会赶不上闭馆 |
| 超出每日结束时刻 | × 5 | 中罚，可以晚点回酒店但不能太晚 |

超长路段惩罚：
```python
for 每段 seg:
    if seg > long_leg_min (默认 45):
        stretch += (seg - 45)² × stretch_factor (默认 0.6)
```
平方项的意义：50 分钟不加多少，120 分钟会重罚。没有这项时，实测出现了「上午圆明园、下午天安门」（221 分钟在路上）的安排。

## 用餐建模

真实行程里必须吃饭。实现方式：`_eval_route` 在计算时刻推进时，遇到午餐窗口 `[11:30, 13:30]` 会：

1. 如果景点会跨过整个午餐窗口（如 11:15 抵达、游览 150 分），**先吃再进馆**
2. 如果抵达时已在窗口内且游览时长较短，**逛完再吃**
3. 如果已过 13:30 还没吃，标记为"已在路上解决"，**不插入虚假的午餐块**

第 3 条很重要：早期版本会在 13:17 插一个"午餐"，时间上荒谬。

## 交通模式

`travel_mode: "hybrid"`（默认，推荐）：

```
若 距离 ≤ 2.5km 且 步行时间 ≤ 30min → 步行
否则 min(步行时间, 驾车时间 + 8min找车等待)
```

8 分钟是打车等待 + 上下车的经验值。

**不含地铁**。国内大城市 3km 以上更可能坐地铁，地铁通常略快于打车，所以这个估算对长距离是**保守上界**（给出的交通时间偏长，行程偏宽松）。想更精确需要接高德/腾讯地图 API（需 key）。

其他模式：`pedestrian` 全程步行（适合古镇、景区内部）、`auto` 全程驾车、`bicycle` 骑行。

**避坑**：OSRM 的 `/route/v1/foot/` 和 `/bike/` 返回的是汽车速度（实测 1688m/180s = 33km/h），不可用于步行。要步行数据必须用 Valhalla 的 `costing: pedestrian`。

## 参数调优

| 参数 | 默认 | 调大的效果 | 何时调 |
|---|---|---|---|
| `w_travel` | 1.0 | 更重视少走路，可能与必去点冲突 | 老人小孩同行 |
| `w_value` | 60 | 更不愿意塞低分景点 | 想少而精 |
| `w_ticket` | 2.0 | 更倾向免费景点 | 预算敏感 |
| `w_balance` | 150 | 每天收工时间更接近 | 讨厌某天太闲/太累 |
| `long_leg_min` | 45 | 允许更长的单段移动 | 郊区景点（长城、迪士尼） |
| `stretch_factor` | 0.6 | 更激进地避免跨区 | 城市很小、不需要跨区 |
| `insert_threshold` | 900 | 更愿意塞点（可能很赶） | 用户要求"多跑几个" |
| `max_pois_per_day` | 6 | 每天上限提高 | 快节奏打卡 |
| `pace` | 标准 | 轻松=0.75（游览时间缩短但容量受限），紧凑=1.25 | 用户节奏偏好 |

**如何验证调参有效**：看 `stats.efficiency`（游览时间 / 总清醒时间）。
- < 60%：交通冗余，路线有问题
- 60–75%：偏松，可以塞点
- 75–88%：健康区间
- \> 88%：太赶，实际执行会崩

## 坐标系

**这是最容易出错的地方。**

- OSM / Valhalla / Photon → **WGS-84**（GPS 原始坐标）
- 高德 / 腾讯 → **GCJ-02**（国测局加密，俗称"火星坐标"）
- 百度 → **BD-09**（在 GCJ-02 上再偏移一次）

北京市区 WGS-84 → GCJ-02 偏移量约 **533m 东 / 155m 北**。不转换的后果：景点落在隔壁街区，路网矩阵全错，地图标记飘在半空中。

`geo.py` 的 `gcj02_to_wgs84` 用迭代反解（30 次收敛到 <0.1m），因为正向变换没有解析逆。

**正确流程**：
1. Photon 拿到 WGS-84 坐标
2. 用 WGS-84 建路网矩阵（Valhalla 也是 WGS-84，直接可用）
3. 渲染前把坐标转成 GCJ-02 叠高德底图

`pipeline.py` 已按此实现：POI 同时存 `lat/lng`（WGS-84）和 `gcj_lat/gcj_lng`（GCJ-02）。

## 缓存

矩阵计算是最贵的（13×13 双模式约 20–30s）。`sources.py` 用坐标哈希做 7 天缓存，存在 `.cache/` 下。

改 POI 顺序不影响缓存命中（哈希基于坐标集合），但增删点会导致全量重算。

## 已知限制

1. **地理编码覆盖**：Photon 对中文小地名一般（"国家博物馆"查不到，"中国国家博物馆"可以）。失败时用模型知识补坐标。
2. **POI 元数据靠人工**：开放时间、门票、游览时长没有免费 API，靠模型判断。可能不准。
3. **不含地铁**：长距离交通时间偏保守。
4. **不做天气**：雨天备选方案需要额外接入天气 API。
5. **单起点**：每天从固定时间出发，不支持"酒店在 A、第二天住 B"的跨城迁移。
