# Trip Optimizer · 行程规划优化器

**不是让 AI 猜景点顺序，而是用运筹学算出来。**

一个给 AI agent 用的旅行行程规划 skill：拿真实路网耗时矩阵，跑多日带时间窗的路径优化（VRPTW 变体），输出可解释的行程方案 + 交互式地图手册。零第三方依赖，纯 Python 标准库。

> 现有 AI 旅行规划工具的普遍做法：让模型凭常识把景点分配到每天，套个模板渲染成攻略。结果经常路线来回折返、跨半个城硬塞、时间算不准。
>
> 这个项目换掉的是最核心的一环 —— **排序和分配到哪一天，交给求解器。**

## 算法

问题形式化：**多日带时间窗的路径规划**（Multi-Day VRPTW 变体）。每辆车 = 一天，时间窗 = 景点开放时间，容量 = 当天可用时长。NP-hard，用启发式。

三段式求解：

```
阶段 1  全局贪心插入
         按 优先级 → 评分 → 游览时长 排序，每个点选"边际代价最低 + 负载最轻"的一天

阶段 2  跨日局部搜索
         补插 / 移动 / 交换 三种邻域动作，用全局总代价判断是否接受

阶段 3  单日路线排序
         2-opt（反转区间）+ or-opt（单点移位）+ LNS 破坏重建（随机摘点重插，跳出局部最优）
```

目标函数加权五项：

```python
cost = 1.0 × 总交通分钟
     + 1.0 × 时间窗违规        # 早到等待 ×0.8、迟到 ×8（强罚）、超出当日时限 ×5
     + 60  × 凑数惩罚           # (5-评分) × (可选程度)，必去点不罚
     + 2.0 × 门票总额
     + 0.6 × Σ(超 45 分钟路段的超出量²)   # 防"上午圆明园下午天安门"
```

详细推导、调参指南、踩坑记录见 [`references/algorithms.md`](references/algorithms.md)。

### 三个容易写错的地方

这三个都是开发过程中真实踩过、被测试抓出来的：

1. **负载均衡必须用"收工时刻"而不是"点数"。** 6 个 30 分钟的快餐点和 2 个 3 小时的博物馆，点数差 3 倍但时间可能一样。用点数均衡会排出「Day1 只 2 个点 14:58 收工、Day3 塞 6 个点」。
2. **跨日改进必须用全局总代价判断。** 用局部两天代价时均衡项不参与，永远不会为了均衡而移动点。
3. **凑数惩罚的方向。** `(5 - priority)` 是反的 —— 会让必去点被罚最重，求解器主动丢掉 priority=1 的景点。正确是 `max(0, priority - 1)`。

## 数据源

不依赖任何需要 API key 的服务。

| 服务 | 用途 | 状态 |
|---|---|---|
| [Valhalla](https://valhalla1.openstreetmap.de) | 真实路网 路线/矩阵，pedestrian/auto/bicycle | ✅ 公开实例，单次 ≤100 点对 |
| [OSRM](https://router.project-osrm.org) | 兜底路线 | ✅ 仅 driving 可靠 |
| [Photon](https://photon.komoot.io) | 地理编码 + 类别检索，支持中文 | ✅ 无需 key |
| 高德瓦片 | 中文底图 | ✅ 可直接引用 |

**已实测不可用**：Overpass 全部镜像（406/超时）、高德/百度 REST API（需 key）、OSM 官方瓦片、CartoDB。

### ⚠️ 坐标系是最大的坑

| 来源 | 坐标系 |
|---|---|
| OSM / Valhalla / Photon | **WGS-84**（GPS 原始） |
| 高德 / 腾讯 | **GCJ-02**（火星坐标） |
| 百度 | **BD-09** |

北京市区两者差 **533m 东 / 155m 北**。不转换的后果：景点落到隔壁街区，路网矩阵全错，地图标记飘在半空。

正确流程：Photon 拿 WGS-84 → 用 WGS-84 建路网矩阵 → 渲染前转 GCJ-02 叠高德底图。`geo.py` 提供双向往返（反解用迭代收敛到 <0.1m，因为正向变换没有解析逆）。

### ⚠️ OSRM 的 foot / bike 是假的

实测 `/route/v1/foot/` 返回 1688m / 180s = **33 km/h** —— 那是汽车速度。要步行数据只能用 Valhalla 的 `costing: pedestrian`。

## 效果

### 北京 · 3 天 · 13 个景点

13 个候选点，必去 4 个（故宫、天安门、天坛、颐和园），步行+打车混合。

- 时间利用率 88%（游览 28.2h / 交通 4.0h / 门票 ¥266）
- 三天收工 17:14 / 18:13 / 17:46，负载均衡
- 必去点 100% 覆盖，无一遗漏
- 求解耗时 50s（13×13 双模式矩阵 20s + 求解 1s，矩阵有 7 天缓存）

### 成都 · 2 天 · 9 个景点（泛化验证）

9 个点全部定位成功，路线符合地理直觉：锦里→武侯祠 3 分钟（确实紧邻），熊猫基地→春熙路 60 分钟（郊区进城）。利用率 87%。

## 交付物

HTML 行程手册是**单文件，完全离线可用**（Leaflet 已内联，约 230KB）：

- 高德中文底图（GCJ-02 对齐）
- 每日真实路网轨迹：步行红色实线 / 打车蓝色虚线，带白色描边保证在密集底图上可见
- 时间轴卡片：抵达/离开时刻、移动时长与距离、门票、开放时间
- 用餐块（午餐/晚餐自动插入，只在实际合理的窗口内）
- 多日切换、地图与卡片联动、打印友好

**全部离线**，不发任何网络请求（用手工构造的耗时矩阵和伪造 plan）。CI 在 Linux / macOS / Windows × Python 3.9 / 3.11 / 3.13 上跑。

覆盖的关键断言：

- 坐标系往返精度 <1e-8、境外坐标不偏移
- Polyline 解码（对照 Google 官方示例）
- 时刻推进与时间窗（抵达时刻计算、闭馆重罚）
- 用餐窗口（11:15 开始的 3 小时景点会先吃饭、14:00 后不插午餐、**时间不得倒流**）
- 求解器（必去点覆盖、闭馆日硬约束、容量受限时正确丢弃）
- 目标函数单调性（交通更长→代价更高、低分备选点更贵、**必去点零惩罚**）
- 渲染（Leaflet 已内联、无 CDN 依赖、内嵌 JSON 可回读）

## 已知限制

1. **不含地铁。** 长距离交通按打车估算，比实际偏保守（行程会略显宽松）。精确需要接高德/腾讯地图 API（需 key）。
2. **POI 元数据靠人工判断。** 开放时间、门票、游览时长没有免费 API，由 agent 或用户填写。可能不准，出发前请以官方为准。
3. **地理编码覆盖有限。** Photon 对中文小地名一般（"国家博物馆"查不到，"中国国家博物馆"可以）。失败时需手工补坐标。
4. **不做天气。** 雨天备选方案需额外接入天气 API。
5. **单起点。** 每天从固定时刻出发，不支持"酒店在 A、第二天住 B"的跨城迁移。
